# RAG 资料问答 Agent 模拟面试总结

## 项目介绍参考答案

我实现了一个基于 RAG 的资料问答 Agent，用于解决用户面对 PDF、Markdown、TXT 等资料时，人工查找信息效率低的问题。

用户上传资料后，系统通过 LangChain 加载和切分文档，使用阿里云百炼 DashScope 的 `tongyi-embedding-vision-flash-2026-03-06` 将文档片段向量化，并存入 Chroma 向量数据库。用户提问时，系统先执行语义检索和相关性阈值过滤，再将可信片段组成 context，交给 `qwen3.6-plus` 生成带引用来源的回答。

实现过程中，我完成了 DashScope 国内模型接口接入、自定义 Embedding 适配器、资料删除后的索引同步、Windows 下 Chroma 文件占用问题处理，以及资料管理、历史记录与越界问题拒答机制。后续可以加入固定评测集、混合检索、rerank、按文档增量索引与多用户权限隔离。

## 已掌握知识点

### 1. RAG 主流程

```text
入库：文档 -> 加载 -> chunk 切分 -> embedding -> Chroma
查询：问题 -> embedding -> 相似度召回 -> 分数过滤
生成：相关 chunk -> context -> prompt -> LLM -> 答案与来源
```

RAG 不是把资料训练进模型，而是在每次回答前先检索资料，再让模型基于资料作答。

### 2. 组件职责

| 组件 | 职责 |
| --- | --- |
| `PyPDFLoader` / `TextLoader` | 读取原始资料并转换为 `Document` |
| `RecursiveCharacterTextSplitter` | 将长文档切成可检索的片段 |
| Embedding 模型 | 将 chunk 和 query 转换为向量 |
| Chroma | 保存向量、文本和 metadata，并执行语义检索 |
| Prompt | 规定回答范围、格式与拒答规则 |
| 聊天模型 | 根据检索到的 context 生成回答 |
| Streamlit | 提供上传、提问、管理与调试界面 |

### 3. 当前技术选型

```text
聊天模型：qwen3.6-plus
嵌入模型：tongyi-embedding-vision-flash-2026-03-06
模型服务：阿里云百炼 DashScope
向量数据库：Chroma
应用框架：Streamlit
编排与文档处理：LangChain
运行环境：conda 环境 Agent
```

聊天模型负责生成语言答案；嵌入模型负责生成供检索比较的固定维度向量，二者不能随意互换。

## 面试问题与标准表述

### Q1：为什么先切分文档，再做 embedding？

文档切分后，每个 chunk 可以单独生成向量，系统能够进行细粒度语义检索。用户提问时只需要将最相关的少量片段交给模型，能够减少 token 和调用成本，也避免整篇文档中的无关内容干扰答案。整篇 PDF 即使能生成向量，也会把多个主题混在一起，检索精度通常较低，并可能超过模型上下文窗口。

### Q2：Embedding 模型和聊天模型有什么区别？

文档加载器负责读取资料；Embedding 模型负责将文档片段和用户问题转成向量，供 Chroma 比较相似度；聊天模型负责阅读检索到的 context 并生成答案。`qwen3.6-plus` 是生成模型，不能代替需要稳定向量输出的 Embedding 模型。

### Q3：为什么加入相关性阈值？

单纯的相似检索即使面对资料外问题，也会返回相对最接近的片段。通过 `similarity_search_with_relevance_scores()` 获取相关性分数，并设置 `min_relevance_score`，可以只让足够可信的片段进入生成阶段；如果没有片段达标，系统直接拒答，从而降低幻觉风险。

```text
阈值过高：正确片段被过滤，出现误拒答。
阈值过低：无关片段进入 context，增加越界回答风险。
```

### Q4：什么是召回？如何排查回答错误？

召回是从大量资料片段中找回可能与问题相关内容的过程，它负责找材料，而不是生成最终答案。

```text
先看召回片段和分数：
  正确 chunk 未召回 -> 检查入库、切分、top_k、阈值、embedding。
  正确 chunk 已召回但回答错误 -> 检查 prompt、context 组织和聊天模型。
```

召回率关注应该找到的相关片段中找回了多少；精确率关注返回的片段中有多少真正相关。

### Q5：`chunk_size` 和 `chunk_overlap` 的作用是什么？

`chunk_size` 表示单个片段长度。太大时可能包含多个主题、检索不聚焦并增加生成上下文成本；太小时可能拆散完整语义，导致片段不足以回答问题。

`chunk_overlap` 表示相邻片段重复的文本长度，用于保护跨越切分边界的关键信息。重叠太大则会产生存储和调用冗余，并让大量相似片段占据有限的召回名额。

### Q6：Prompt 能完全防止幻觉吗？

不能。Prompt 只是软约束，模型仍可能在资料不足时尝试回答。本项目通过相关性阈值在生成前过滤无关证据，同时展示程序实际检索的来源。后续还可以加入 rerank、答案证据校验、固定评测集和更严格的拒答判断。

### Q7：如何接入 DashScope？

DashScope 的聊天模型提供 OpenAI 兼容接口，因此项目使用 LangChain 的 `ChatOpenAI`，配置 DashScope `base_url` 和 `qwen3.6-plus` 模型。

`tongyi-embedding-vision-flash-2026-03-06` 使用 DashScope 多模态 Embedding 接口，其请求与响应结构不符合默认 `OpenAIEmbeddings` 协议，因此项目实现了 `DashScopeMultimodalEmbeddings` 适配器，为 Chroma 提供统一的 `embed_documents()` 和 `embed_query()` 方法。

### Q8：删除原始文件后为什么还要同步索引？

原始文件是可信知识源；Chroma 是包含 chunk、metadata 和向量的可检索副本。删除原文件并不会自动删除向量库中的旧片段。如果不同步，系统仍可能检索到已删除内容，产生知识状态不一致和引用不可追溯的问题。

当前 Demo 在删除资料后全量重建索引，优点是简单可靠；大规模系统应为文档分配 `document_id`，按文档精确增删 chunk，支持增量维护。

### Q9：如何增强纯向量检索？

纯向量检索擅长语义相似，但对产品编号、错误码、人名、缩写等精确术语可能不稳定。可以加入 BM25 或全文关键词检索，与向量召回组成混合检索；再加入 rerank，对候选片段做更细致的相关性重排，最终只将高质量证据交给模型。

```text
候选召回：向量检索 + 关键词检索
候选精排：rerank
最终生成：最佳片段 + prompt + LLM
```

### Q10：多轮对话应如何实现？

不应默认把模型回答写回知识库，因为生成内容可能存在错误，继续检索会放大错误。更合理的方式是保存近期对话历史，将包含代词或省略信息的追问改写为独立问题，再从原始知识库检索可信资料。

```text
对话历史：用于理解用户当前意图
原始知识库：用于提供事实依据
```

### Q11：多用户系统如何保证权限安全？

权限控制必须发生在检索之前或检索过程中，而不是回答生成后再隐藏结果。应为文档和 chunk 写入 `owner_id`、`knowledge_base_id`、`visibility` 等权限元数据，并基于当前用户权限过滤可召回范围。生成阶段的 context 与来源展示必须使用同样的授权结果。

### Q12：如何管理 API Key？

本地开发将真实 `DASHSCOPE_API_KEY` 放入 `.env`，并通过 `.gitignore` 防止提交；仓库只保留 `.env.example`。部署场景应通过环境变量、CI/CD Secret 或密钥管理服务注入 Key。

如果 Key 泄露，应立即禁用或轮换旧 Key，再清除仓库当前内容与历史泄露痕迹，并检查是否出现异常调用和费用。

### Q13：为什么向量召回后还需要 Rerank？

Embedding 召回负责从大量资料中快速筛出候选片段，重点是速度和尽量不遗漏；Rerank 负责对候选片段进行更精细的相关性评分与重新排序，重点是让最能回答问题的证据排到前面。

仅依靠向量相似度，可能会返回一些主题相关但不能直接回答问题的片段，也可能让内容相近的重复片段占据最终 `top_k`。生产级流程通常会先召回较多候选，再通过 Rerank 精排，最后只把高质量证据交给聊天模型。

```text
问题 -> 混合/向量召回候选 -> Rerank 精排 -> 取最佳片段 -> LLM 生成
```

### Q14：如何判断参数调整或检索升级真的有效？

不能只看某一个问题的表现。我会建立固定评测集，覆盖：

```text
资料中明确有答案的问题
语义改写但应召回的问题
需要综合多个片段的问题
资料中没有答案、应拒答的问题
包含精确术语、编号或人名的问题
```

每次修改 `chunk_size`、`top_k`、相关性阈值，或加入混合检索和 Rerank 后，都用同一批问题比较正确 chunk 是否被召回、无关片段是否减少、拒答是否准确、答案是否有来源支撑，以及延迟和 API 成本是否可接受。

### Q15：用户上传 PDF 到看到答案，完整调用链是什么？

```text
Streamlit 上传文件
  -> save_upload() 保存到 data/uploads/
  -> reset_index() / ingest_all() 重建索引
  -> PyPDFLoader / TextLoader 加载 Document
  -> RecursiveCharacterTextSplitter 切分 chunk
  -> DashScopeMultimodalEmbeddings 生成向量
  -> Chroma 保存 chunk、向量和 metadata

用户提问
  -> ask()
  -> 问题 embedding
  -> Chroma 召回并按相关性阈值过滤
  -> _format_context() 组织证据
  -> ChatPromptTemplate 构造提示词
  -> qwen3.6-plus 生成答案
  -> 页面展示答案和真实来源，写入问答历史
```

### Q16：全量重建索引有什么优缺点？大规模知识库如何优化？

当前 Demo 删除资料后全量重建 collection，优点是实现简单、数据一致性容易保证，不容易残留已删除资料的旧向量。缺点是资料量变大后耗时和 Embedding API 成本都会增加，删除单个文件也要重新处理全部剩余资料。

如果知识库规模达到十万份文档，我会为每份资料生成稳定的 `document_id`，将它写入所有 chunk 的 metadata。新增、修改或删除资料时只处理对应文档的向量，实现增量索引维护；多用户场景再按 `knowledge_base_id` 或 `tenant_id` 做隔离与过滤。

### Q17：从 Demo 升级为团队可用产品，还需要什么能力？

至少需要以下能力：

```text
权限隔离：区分个人与团队知识库，检索时执行授权过滤。
检索增强：加入混合检索与 Rerank，提高术语和复杂问题效果。
评测反馈：维护标准问题集，记录来源准确性和用户反馈，避免升级回退。
增量索引：按文档维护向量，降低更新成本。
解析能力：支持扫描 PDF/OCR、表格与更丰富文档结构。
监控审计：统计延迟、调用费用、失败率并记录敏感操作。
```

### Q18：对话历史为什么不能直接写回知识库？

知识库文档是用户上传或系统确认过的可信原始资料；对话历史包含用户表达和模型生成答案，主要用于理解上下文。模型回答可能存在误解、遗漏或幻觉，如果默认将回答向量化写回知识库，后续检索可能继续引用生成错误，形成知识污染和错误放大。

支持多轮问答时，更合适的做法是利用近期对话历史将追问改写为独立问题，然后仍然检索原始资料作答。

### Q19：索引失败或引用错误时，如何按步骤排查？

索引失败时：

```text
1. 查看异常与日志，定位发生在加载、切分、Embedding 还是 Chroma 写入。
2. 检查原始文件格式、PDF 是否能解析。
3. 检查 DashScope Key、模型名、接口地址和 API 返回值。
4. 检查 chunk 数量是否合理、collection 是否写入成功。
5. 排查本地数据库文件锁或运行环境冲突。
```

引用或答案错误时：

```text
1. 用“检索”页面直接查看召回的 chunk 与分数。
2. 正确 chunk 未被召回：调资料入库、切分、top_k、阈值、embedding 或检索策略。
3. 正确 chunk 已召回但答案错误：调 context、prompt 或聊天模型。
4. 将出错问题加入评测集，避免后续回归。
```
